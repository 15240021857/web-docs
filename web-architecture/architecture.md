# 架构设计

## 是什么

<!-- - 要考虑的问题参考：https://mp.weixin.qq.com/s/gGWrjUR7Uc90mQKqRVBM6g -->

- 设计整个项目的分层、规则、约束，不让开发人员乱写代码。
- 各个层级做自己的事，职责清晰，方便维护，以后方便扩展。

## 为什么要设计架构

- **没有架构的项目**，开发人员无约束，自由的写代码，维护起来很困难，比如想找一段 `axios调API接口` 的代码，它可能在apis里、组件里、hooks里、store里、utils里，无法预测……
- **有架构的项目**，开发人员有约束，写代码时要遵守架构分层规则，维护起来比较容易，比如想找一段 `axios调API接口` 的代码，它分配在 `数据层` 里，即 `/apis` 文件夹下，不会出现在其他层级。

## 架构分层怎么分

**前端架构分层**：

| <span style="white-space: nowrap;">层级</span>       | 负责的代码                                       | 约束                             | 模块                                                             |
| ---------------------------------------------------- | ------------------------------------------------ | -------------------------------- | ---------------------------------------------------------------- |
| <span style="white-space: nowrap;">视图层</span>     | 用户界面代码，用户看得见摸得着                   | 不写复杂逻辑                     | .vue组件、布局                                                   |
| <span style="white-space: nowrap;">业务层</span>     | 业务规则、表单校验，如订单状态流转、满50减10元等 | 不碰Dom, 不写样式                | hooks、store                                                     |
| <span style="white-space: nowrap;">数据层</span>     | 获取api接口数据、数据转换、缓存                  | 调用request函数，不用每次写axios | 、apis请求、接口TS类型、统一请求拦截、错误提示                   |
| <span style="white-space: nowrap;">基础底层</span>   | 纯工具                                           | 无业务逻辑，被上面三层调用       | utils、request封装、通用组件库、字典值、全局css                  |
| <span style="white-space: nowrap;">工程构建层</span> | 负责源码编译、环境注入、打包产物、自动化         | 无业务逻辑                       | vite.config.ts、.env、package.json、eslint、tsconfig、Dockerfile |

## 目录结构

### 方案A: 按文件类型分 （传统划分）

1. 适合（小/中/大）型项目，比较通用

```text
src
├── api               // 所有接口，按业务拆分文件 order.js user.js
├── assets            // 静态资源
├── components
│    ├── base        // 全局基础组件：按钮、弹窗、输入框（无业务）
│    └── business    // 全局业务组件：地址选择、上传（跨页面复用）
├── hooks             // 全局复用hooks（跨页面）
├── router
├── store
├── utils
└── views             // 页面入口，**模块内部内聚**（重点！）
     └── order
          ├── components   // 订单页面私有组件（只订单用）
          ├── index.vue    // 订单主页面

```

✅ 优点：

- 新人一眼看懂，几乎所有后台脚手架默认这个结构，**团队上手成本最低**

❌ 缺点（项目变大后暴露）：

- 改订单，要去 4 个地方：`views/order`、`api/order.js`、`hooks/useOrder.js`、`store/order.js`，跨文件夹跳转。
- 业务膨胀后，`api`、`hooks`文件夹下几十上百个 js 文件，查找麻烦。

### 方案B: 按模块内聚（业务优先划分）

1. 适合
   - 超大型、复杂的项目
   - 项目规模大、多个项目组人员维护、模块多，分开解耦，方便维护，不打扰其他模块

```text
src/
├── assets     静态资源（图片字体）
├── common     全局基础：全局组件、通用工具、全局样式
├── modules    【业务模块】
│    ├── order 订单模块
│    │   ├── components 订单内部组件
│    │   ├── api 订单接口
│    │   ├── hooks 订单业务逻辑
│    │   └── index.vue 订单主页面
│    └── user 用户模块
├── router 路由（相当于门店导航牌，指引用户去哪个页面）
└── store 全局状态（跨页面共享数据，比如登录信息，相当于门店公共台账）
```

✅ 好处：**订单相关所有东西，全部放 order 文件夹。改订单，只进这一个文件夹。**，适合多团队并行开发，每个团队负责一个模块，互不干扰。

❌ 缺点（公共模块抽取问题明显）：- 习惯按文件类型分的开发人员，有上手切换成本。- 边界难界定，架构需要约定公共模块抽取规则，否则模块之间互相引用，造成模块耦合严重。- 路由配置，默认放在顶层，跟模块物理分离，不放到业务模块下，需额外做路由聚合。- 单模块代码逐渐庞大后，还需要内部再分层，子模块又嵌套子子模块，复杂度上升。

### 方案C: 混合模式：按文件类型分 + 模块内聚（⭐最推荐 最通用）

1. 适合几乎所有项目
   - 规模一般的项目，按文件类型分即可
   - 中大型项目，规模越来越大，复杂模块采用模块内聚目录单独处理
   - 超大型项目，与上同理

```text
src
├── api                # 【小模块接口】放这里（比如简单字典、简单个人中心）
├── hooks              # 【全局通用hooks】放这里（防抖、表单校验通用逻辑）
├── components
│   ├── base           # 基础组件
│   └── business       # 全局跨模块业务组件
├── store              # 全局状态：登录、全局配置
├── utils
├── types              # 全局公共类型
├── router
├── views
│   ├── order          # 👉 大模块，全部内聚
│   │   ├── components # order私有组件
│   │   ├── api.ts     # 订单专属接口
│   │   ├── hooks      # 订单业务hook（useOrderSubmit）
│   │   ├── store.ts   # 订单模块pinia
│   │   ├── types.ts   # 订单类型定义
│   │   └── index.vue
│   └── dashboard      # 👉 简单小页面，就一个vue，没有配套api/hooks，直接放这
│       └── index.vue

```

✅ 优点

1. 渐进改造：不用一次性全量重构现有项目，非常适合存量项目迭代；
2. 大业务模块高内聚：改订单只进 order 文件夹；简单页面不用新建一堆子文件，减少空文件夹；
3. 符合主流团队目录习惯：一般都是按文件类型分

⚠️ 风险点（**这就是容易混乱的根源，必须定死规则**）

> 最大问题：多人判断标准不一致：到底这个模块算 “大模块” 还是 “小模块”？

- 规则必须写死（写到架构文档）：
  - 满足任意 2 条 → 在 views 下内聚：页面≥3、独立业务域、有独立状态、多个私有组件、接口≥ 8个；
  - 简单页面（纯展示，1~2 个接口，无内部组件）→ 不新建内部 api/hooks，复用顶层 api。

- 禁止：**一个业务模块的代码只能存在一处，不能两地维护！** 禁止同一个业务，一部分 api 写在顶层`api/order.ts`，一部分写在`views/order/api.ts`。

> 一句话总结：**定好判断规则 → 灵活好用；只口头凭感觉判断 → 越写越分裂。**
