# 前端基建
## 介绍
- 经常听到前端基建这个概念，但还没有明确过它到底包括哪些~
- 前端基建是一个系统性工程，核心目标是提效、降本、保质，让团队从重复劳动中解放出来，聚焦业务创新

## 项目脚手架与工程模板
脚手架是基建的"第一入口"，解决的是新人上手慢、项目初始化标准不一的问题。
- CLI 工具：封装一个 xxx init 命令，一键生成项目骨架，预置好 ESLint、Prettier、TypeScript、Git Hooks 等配置，做到"一步搞定所有事"
- 项目模板仓库：按业务场景沉淀模板（中后台模板、H5 模板、跨端模板等），新人选模板即可开工
- Monorepo 管理：使用 pnpm workspace / Turborepo 统一管理多个子项目，将组件库、工具库、业务应用放在同一仓库中，packages 放公共模块，apps 放业务应用
> 落地建议：初期不必自研 CLI，可以先用 create-vite 等官方脚手架 + 团队模板仓库起步，后期再按需封装。
## 开发规范与代码质量
规范是团队协作的"契约"，核心是让所有人写出的代码风格一致、质量可控。
- 代码风格统一：ESLint（规则检查）+ Prettier（格式化）+ Stylelint（CSS 规范），三件套配合 Husky 在 git commit 前自动拦截不合规代码
- 提交规范：Commitlint + Commitizen，强制要求 commit message 遵循约定式格式（如 feat:、fix:、chore:），保证变更历史可追溯
- Code Review 机制：制定 CR 规范，重点关注逻辑错误与性能问题，推动知识共享
- TypeScript 类型约束：提前暴露类型错误，减少运行时 bug
> 落地建议：规范一旦确定就严格执行，但初期不要定太多规则，从"普遍性 + 高频"的痛点入手逐步收敛。
## 组件库与设计系统
组件库是前端基建中复用价值最高的部分，直接减少重复开发。
- UI 组件库：基于 Ant Design / Element Plus 二次封装，或直接自研，覆盖团队高频使用的组件（表格、表单、弹窗、上传等）
- 业务组件库：将跨项目复用的业务模块（如文件上传器、富文本编辑器、图表渲染器）沉淀为独立包
- Hooks 库：抽取通用的组合式函数（如 useRequest、useTable、useAuth），提升逻辑复用
- 工具函数库：日期处理、数据格式化、权限校验等通用工具统一封装
- 文档站点：用 Storybook / Dumi / VitePress 搭建组件文档，先展示可交互 Demo，再提供 API 说明
> 落地建议：小团队可以先做"业务组件库 + 工具函数库"，不必追求大而全的 UI 库。组件命名、版本管理要标准化，方便查找和引用。

## 构建系统与性能优化
构建系统决定了开发体验和产物质量。
- 构建工具选型：Vite 因其快速启动和按需编译已成为主流首选，大型项目可考虑 Bazel 实现毫秒级增量构建
- 代码分割与按需加载：通过动态 import() 和 splitChunks 策略，减少首屏加载体积
- 静态资源优化：图片压缩、字体子集化、CSS 提取、contenthash 缓存策略
- 性能监控：追踪核心 Web 指标（LCP、FID、CLS），建立性能基线，定期生成 Lighthouse 报告
- 自动化性能检测：基于 Node 实现定时性能扫描，建立性能数据大盘和红黑榜

## CI/CD 流水线
CI/CD 是基建中投入产出比最高的环节之一，实现"提交即部署"。
- 自动化流水线：配置 GitLab CI / GitHub Actions / 阿里云效等，push 或 PR 时自动执行：lint → test → build → deploy preview
- 代码合规检测：在流水线中集成 Lint 检测、兼容性 API 检测、依赖安全扫描（npm audit），检测不通过则阻塞发布
- 多环境管理：开发、测试、预发、生产环境配置分离，支持一键切换和回滚
- 容器化部署：Docker + Nginx 标准化部署方案，避免"在我机器上是好的"问题
> 落地建议：初期可以用 GitHub Actions 或阿里云效快速搭建，先把 lint + build + deploy 跑通，再逐步加入测试和安全扫描。

## 监控与可观测性
上线不是终点，监控是保障线上稳定的关键。
- 错误监控：集成 Sentry / LogRocket 捕获运行时异常，第一时间发现并定位线上 bug
- 埋点体系：统一埋点规范和 SDK，建立"开发-数据-产品"的统一数据语言，支撑业务决策
- 用户行为分析：可视化热图、用户路径分析、用户画像等数据化能力
- 性能监控：Web Vitals API 采集真实用户性能数据，设定告警阈值

## 测试体系
测试是质量的"守门员"。
- 单元测试：用 Vitest / Jest 覆盖工具函数和核心业务逻辑
- E2E 测试：用 Playwright / Cypress 验证关键用户路径（如登录、支付流程）
- 自测 CheckList：制定标准化的自测清单，减少提测后的 bug 数量

##  文档与知识沉淀
文档是基建能否持续运转的"生命线"。
- 技术文档：架构设计文档、项目初始化指南、组件使用手册、CI/CD 配置说明
- 文档工具：Docusaurus / VitePress / GitBook 搭建文档站，Confluence / 飞书文档做内部 Wiki
- 接口契约：通过 Apifox / Swagger 维护接口文档，支持自动 Mock，减少前后端联调成本

## 落地策略总结
前端基建不是一蹴而就的事，关键在于渐进式演进：
表格
| 阶段 |	重点 |	产出 |
| ----   | ----  | ---- |
|起步期 |	规范先行 + 脚手架 + CI/CD |	ESLint/Prettier 配置、项目模板、自动化构建部署 |
|成长期|	组件库 + 工具库 + 测试体系|	业务组件库、工具函数库、单元测试覆盖|
|成熟期|	监控体系 + 性能优化 + 数据驱动|	错误监控、埋点体系、性能大盘|

## 几个核心原则值得牢记：
- 从业务痛点出发，不要"从方案出发找场景"，避免学屠龙之技却发现没有龙
- 凡是建设，必有数据，用数据证明基建带来的投入产出比
- 与业务阶段匹配，"如果你只需要一根针，千万不要去磨铁棒"
- 文档驱动，每个模块都要有文档，避免"人走知识失"
