# 测试体系

## 是什么？
- 测试是质量的"守门员"。
- 单元测试：用 Vitest / Jest 覆盖工具函数和核心业务逻辑
- E2E 测试：用 Playwright / Cypress 验证关键用户路径（如登录、支付流程）
- 自测 CheckList：制定标准化的自测清单，减少提测后的 bug 数量


## 单元测试
### 是什么
- 单元测试是指对代码中的独立单元（测试用例）进行测试，以验证其是否符合预期。
- 可配合ci/CD工具，自动执行单元测试，确保代码质量。
### 哪些框架
- vue的单元测试：vitest
- react的单元测试：jest

## e2e测试
核心功能，需要在真实环境中测试，确保功能正常运行。
- 端侧测试：cypress
- 客户端测试：playwright

## 冒烟测试
### 1. 什么是冒烟测试

> 
> 版本刚部署完，**先跑一遍最核心、最主干的流程**，快速判断这个版本能不能用，有没有致命 bug。
> 取名来源：就像新焊完电路板，通电先看会不会冒烟；冒烟 = 直接报废，版本直接打回，不用再深入细测。

- **目的**：验证主流程通不通，阻断严重问题，避免后续浪费时间。
- **范围极小**：只测核心路径，**不做细粒度功能、边界、异常测试**。
- 谁执行：测试人员；**前端也经常要做前端页面的冒烟自测**。

> 
> 例子：一个后台系统：登录→首页→打开核心菜单→新增一条数据→提交。这条链路走通，冒烟就算过。

## 二、前端对测试用例要做什么

### 1. 开发阶段

1. **评审测试用例**
   - 看测试同学写的用例有没有漏掉交互、特殊场景
   - 有没有理解错需求；复杂交互、动画、弹窗、兼容场景有没有覆盖
   - 发现问题：提出修改建议，提前对齐，减少后期返工
2. **对照用例做自测**（最重要）
> 
> 不是让你 100% 跑完所有测试用例，但是**主流程用例一定要过一遍**
   - 主干功能是否和需求一致
   - 按钮、弹窗、表单、跳转、接口请求有没有问题
   - 常见异常：网络失败、空数据、超长文本

### 2. 提测后

- 测试提 bug 过来，对照 bug 复现，修复；
- 修复完，**自己再验证一遍**，再转给测试回归。

> 
> 简单一句话：测试用例是标尺；前端要看懂、查漏、自测、修完复现。

## 前端自测一般测哪些内容

### ✅ 1. 功能自测（主干）

- 页面跳转是否正确
- 增删改查、提交表单、弹窗确认 / 取消
- 表单校验（必填、格式、长度）
- 接口成功 / 失败场景，错误提示有没有出来
- 数据回显、列表刷新、分页、搜索筛选

### ✅ 2. UI & 样式自测（前端重点）

- 页面布局有没有错乱、文字溢出
- 不同分辨率：PC 大屏、小窗口；移动端适配
- 浏览器兼容：Chrome、Edge（项目要求 Safari/Firefox 也要测）
- 字体、颜色、间距、图标是否和 UI 稿一致

### ✅ 3. 交互自测

- 加载状态 loading、禁用状态、点击防抖
- 弹窗关闭、返回上一页、路由缓存
- 动画效果、hover、点击反馈

### ✅ 4. 边界 & 简单异常自测（少量）

- 输入超长文字
- 列表无数据（空状态页面）
- 断网刷新看报错提示

> 
> ❗前端自测 ≠ 完整测试；自测通过只是代表**可以提测给测试同学**，不能代替正式测试。

## 前端上线流程完整串联（结合冒烟）

1. 本地开发完成 → **前端自测主干流程**
2. 打包部署到 **FAT 环境** → 测试执行完整测试 + **冒烟测试**
3. bug 修复完毕，版本冻结
4. 部署到 **预发布环境** → 再跑一遍**冒烟测试**（主干流程）
5. 预发验证无问题 → 发布线上生产环境
6. 上线后再做一次线上冒烟，确认没崩

> FAT 环境（Functional Acceptance Test，功能验收测试环境）
