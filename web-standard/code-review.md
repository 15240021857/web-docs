# 代码审查 code review

面向前端小组的日常流程：平时异步看 PR，每周四固定 40 分钟一起过一轮。目标不是把所有提交看完，而是把风险高、可复用、值得统一认知的代码摊开。

## 是什么？

Code Review 是合并前或合并后，由他人检查代码的过程。对小团队来说，它其实是两件事叠在一起：

| 类型 | 何时做 | 谁做 | 目的 |
| --- | --- | --- | --- |
| **日常 PR Review** | 提测 / 合入前 | 指定 1～2 个评审人异步看 | 拦缺陷、对齐实现，保证能合 |
| **周四会审** | 每周四 40 分钟 | 全组一起过 | 对齐标准、传经验、挑共性问题 |

周四会审**不是**把一周提交从头看到尾，也**不是**替代日常 PR Review。没有日常 Review，周四 40 分钟只会变成走过场；没有会审，日常 Review 容易各看各的，标准永远统一不起来。

会审看的是 **PR / 改动包**，不是单条 commit。一条 `fix: 改文案` 和一次「抽公共表格组件」信息量完全不同，按 commit 数排队一定审不过来。

## 解决什么问题？

- **线上问题进仓库太晚**：样式错、接口没兜底、权限漏判，往往合进去才被发现。
- **只有作者懂这块**：公共 hooks、请求封装、路由守卫只有一个人熟，请假或离职就卡住。
- **同一类问题反复出现**：列表空态、loading、重复请求、组件该抽不抽，每个人各写一套。
- **规范停在文档里**：命名、目录、状态放哪，文档有，合并时没人按这个看。
- **40 分钟不够、提交太多**：一周可能几十个 commit。不筛选重点，会审要么超时，要么只挑好讲的无关痛痒。
- **评审变成挑刺或开会聊天**：纠结空格、变量名，或变成需求讨论，代码本身没过几行。

周四会审要解决的，是后四条：在固定短时间里，只过「值得全组知道」的改动，并留下可执行的结论。

## 怎么做？

### 1. 先把日常 PR Review 跑起来

周四 40 分钟审不完一周的量，必须把「能不能合」放在平时。

**合入门槛（前端小组够用）：**

- 每个 PR 至少 1 个评审人 Approve（作者不能自己过自己）。
- CI 过：lint / 单测 / 构建。能自动拦的，会议里不要再聊。
- 描述写清：改了什么、为什么改、怎么验、已知坑。没描述的 PR 可以直接打回。
- 超过约 400 行业务改动，拆 PR 或在描述里标「请重点看哪几个文件」。

**评审人看什么（按这个顺序，别从命名开始）：**

1. 需求是否做对，有没有漏空态 / 错误态 / 权限。
2. 有没有改到公共层：组件、hooks、utils、请求、路由、store、构建配置。
3. 和现有写法是否一致，该复用的有没有重复造。
4. 明显性能或安全问题：列表无虚拟化却一次渲染过多、图片过大、`innerHTML`、token 进日志等。
5. 格式、命名交给 ESLint / Prettier / 提交规范，人工不纠结。

**给意见的方式：**

- 必须改：不改会出 bug 或埋雷，阻塞合并。
- 建议改：有更好写法，不阻塞，作者判断。
- 仅供了解：记录下来，周四再讲。

日常 Review 发现「这个值得全组看」，在 PR 上打标签 `会审候选`，周四主持人直接从这里捞，不用再翻全部提交。

### 2. 周四会审只做一件事：过 1～2 个重点

建议固定：**每周四下午，40 分钟，摄像头 / 投屏，全员到。** 轮流主持，避免永远是组长在讲。

#### 会前怎么从一堆提交里找出重点

主持人在**周四中午前**做完选题，不要开会当场翻仓库。

**从哪捞（优先从上到下）：**

1. 本周带 `会审候选` 的 PR。
2. 本周已合并、改了公共层的 PR（`components/`、`hooks/`、`utils/`、`api/`、`store/`、`router/`、构建和 CI）。
3. 行数大、文件多、或连改好几个业务模块的 PR。
4. 线上 bug / 回滚对应的修复 PR（看根因，不看补丁本身）。
5. 新人第一次合入的非琐碎改动（带教，不是找茬）。

**直接跳过：**

- 文案、样式微调、配置项、lockfile。
- 纯文档、注释。
- 和现有页面同一套 CRUD 模板的新页面。
- 已经在日常 Review 里充分讨论、没有新认知的 PR。

**怎么打分（每个候选看三个问题，选分最高的 1～2 个）：**

| 维度 | 问一句 | 高分信号 |
| --- | --- | --- |
| 影响面 | 会不会被别人复用或踩到？ | 公共组件 / 请求 / 权限 / 路由 |
| 风险 | 错了会不会出线上问题？ | 资金、权限、脏数据、难以回滚 |
| 教学价值 | 全组看完能不能少犯一次错？ | 新模式、踩坑、值得统一的写法 |

一周只选 **1 个主讲 + 1 个备选**。主讲预估能讲 25 分钟；备选 10 分钟，时间不够就下周四。贪多一定超时，超时一定变水。

**作者会前准备（5 分钟就能写完，发到群里）：**

- 一句话：这次改什么、为了什么。
- 重点文件 3～5 个（带路径），不要甩整个 diff。
- 自己觉得不稳的地方、取舍过的方案。
- 希望大家帮忙看的 1 个问题（比「大家随便看看」有用）。

主持人会前把链接、准备说明、议程发群。没准备的，本周不讲，换备选。

#### 40 分钟怎么切

设一个计时员（可以就是主持人），到点就切，不要「再看两眼」。

| 时间 | 做什么 | 注意 |
| --- | --- | --- |
| 0～3 分钟 | 主持人宣布本周 1～2 个题目，以及今天**不看**什么 | 防止开场就扯需求 |
| 3～8 分钟 | 作者按「背景 → 方案 → 重点文件 → 自己的疑问」讲 | 不要从第一行念到最后一行 |
| 8～30 分钟 | 对着重点文件讨论。每人一次只提一件事 | 主持人打断跑题和格式之争 |
| 30～36 分钟 | 有时间再扫备选，或快速过 1 个「反面教材」小修复 | 讲根因，不讲谁的锅 |
| 36～40 分钟 | 主持人复盘：结论、待改项、谁来改、记到哪 | 没记下来的讨论等于没开 |

投屏只打开作者列的 3～5 个文件，以及和结论相关的片段。禁止整页滚动「大家看看有没有问题」——40 分钟里这是最废的用法。

**讨论时只用三种结论，当场说清：**

- **要改**：指出文件和改法，指定人，下周四前或下一个迭代关掉。
- **形成约定**：例如「列表必须有空态和错误态」「公共 hooks 放 `src/hooks`」。会后补进规范，下次当检查项。
- **保持现状**：记录为什么不改，避免下周重复争论。

#### 会后闭环（否则下周还在重复讲）

主持人当场在群里或文档里记三行即可，不必写长纪要：

```text
日期：2026-09-12
过了：#123 公共表格抽离
结论：筛选条件和表格拆开；分页状态进 URL
待改：@张三 本周把示例页改掉
新约定：新增列表页必须带空态 / 错误态 / loading
```

待改项要有人和时间。能开 issue / 跟在原 PR 上就不要只留在聊天记录。新约定补到规范文档，下次日常 Review 按这个拦。

### 3. 前端会审优先看这些，而不是所有 diff

时间紧，按下面清单扫作者标出的文件，够用了。

**值得停下来的：**

- 公共组件 / hooks 的 API 是否好用、会不会把业务细节漏进去。
- 请求：错误是否到用户可见，有没有重复请求、竞态（后发先至）。
- 状态：该在组件、全局 store，还是 URL；刷新 / 回退会不会丢。
- 路由和权限：未登录、无权限、404 有没有漏。
- 列表和表格：分页、空态、加载、删除后的页码。
- 明显性能：大列表、重渲染、大图、首屏接口瀑布。
- 安全：`v-html` / `dangerouslySetInnerHTML`、密钥进仓库、token 打进 console。

**会议里直接跳过：**

- 空格、引号、分号、import 顺序。
- 「我觉得这个名字不够好」且不影响理解。
- 需求该不该做——那是需求评审，会后另开。

### 4. 角色固定，轮流当，避免变成组长独角戏

| 角色 | 谁 | 职责 |
| --- | --- | --- |
| 主持人 | 每周轮换 | 选题、控时、打断跑题、写三行纪要 |
| 作者 | 被选中的 PR 作者 | 会前发重点文件，会上讲背景和取舍 |
| 主评 | 日常 Review 过这个 PR 的人 | 先提已经确认的风险，避免全组从零读 |
| 计时 | 可与主持兼任 | 到点切环节 |

新人不适合一上来当主持人，但适合当作者讲自己的 PR，或会后整理「新约定」。老人少讲「我当年」，多讲「这里以后统一怎么写」。

### 5. 几种常见卡法，按这个处理

**「这周提交太多，不知道过哪个」**  
只看带标签的、改了公共层的、出过线上问题的。其余当没发生。选不出来就选「行数最大的公共文件改动」，不要选业务文案 PR 凑数。

**「40 分钟只过了一个函数」**  
多半在纠结风格或方案细节。主持人 2 分钟内让双方各说利弊，然后三选一（要改 / 成约定 / 保持），继续往下。

**「没人说话」**  
主持人点名主评先讲已发现的问题；再点一名「请只提一个你最担心的点」。禁止「我没问题」连着三个人。

**「变成批斗」**  
只对代码不对人。问「这段在弱网会怎样」，不问「你怎么没想到」。有情绪就休会，问题记下来私下对齐。

**「讲的人准备了 20 页」**  
会审不是分享会。超过 5 分钟背景介绍，主持人打断，切到文件。

**「审完没有后续」**  
没有待改负责人和日期，这周会审作废。主持人有权把「只讨论不落地」的题目下周四重开。

**「人少 / 远程 / 有人请假」**  
3 个人也能开。请假的人事后看纪要和录屏（若有）。不要因为缺人就取消——一取消就很难恢复固定节奏。

### 6. 建议的落地节奏（先跑 4 周）

不要一上来上工具、上检查表、上强制打分。按四周把习惯立住：

1. **第 1 周**：定时间、定主持人轮换表；只选 1 个公共代码 PR 走完 40 分钟流程；写出第一份三行纪要。
2. **第 2 周**：日常 PR 开始打 `会审候选`；评审意见区分「必须 / 建议 / 会审再讲」。
3. **第 3 周**：把上周约定补进规范，日常 Review 按新约定拦一次。
4. **第 4 周**：复盘这四周——有没有重复问题减少、会审是否总超时、选题是否总是「好讲不好用」。只改一处规则，不要推翻重来。

工具保持现有即可：GitLab / GitHub PR、群消息、一份会审纪要文档（或项目 wiki 一页）。缺的不是平台，是「谁选题、谁控时、谁盯待改」。

### 一页对照（打印或置顶群公告）

```text
日常：PR 要有描述 + 1 人 Approve + CI 过；公共改动打「会审候选」
选题：每周四中午前定 1 主讲 + 1 备选；看影响面 / 风险 / 教学价值
跳过：文案、样式、模板 CRUD、lockfile、纯格式
40 分钟：3 宣布 → 5 作者讲 → 22 看重点文件 → 6 备选 → 4 记结论
结论只有三种：要改（有人有期）/ 成约定 / 保持现状
会后：三行纪要进群；约定补规范；待改不跟踪就等于没开
```
