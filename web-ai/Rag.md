# RAG 企业私有知识库问答系统

## 定义
为大模型外挂上企业内部私有的知识库文档，让大模型能参考企业内部文档资料来回答问题，或者指导agent工作。

## 解决哪些痛点
1. 痛点一：大模型没有企业内部资料
- RAG可以让大模型参考企业内部资料
2. 痛点二：企业内部资料可能是私有的保密的，不能喂给外部大模型
- 需要企业内部自研，因为Dify这种方案虽然成熟，但暂无法做到企业自己控制访问权限。

## 向量数据库选型总结：Chroma / pgvector / Milvus

### 1. 三者总体对比

| 维度 | Chroma | pgvector | Milvus |
|---|---|---|---|
| 本质定位 | 轻量嵌入式向量库，AI 原型工具 | PostgreSQL 向量扩展插件 | 专用分布式向量数据库 |
| 部署复杂度 | 最低，`pip install` 即可进程内运行 | 低，复用现有 PostgreSQL | 高，生产需 etcd、MinIO、Proxy、Coordinator 等组件 |
| 运维成本 | 低，但缺少企业级支持 | 最低，备份/监控/权限/事务复用 PG | 最高，需要专门运维/DB 人力 |
| 数据规模适配 | 十万级以内较合适，几十万级开始变慢，百万级接近上限 | 百万级较稳，单机大致 500 万～千万级 | 千万级到十亿级，大规模场景技术最匹配 |
| 性能特点 | 小规模够用，单节点架构 | HNSW 百万级可做到数十毫秒；无法多核并行扫描/GPU 加速 | 支持多种索引、存算分离、并行构建/查询，大规模毫秒级 |
| 扩展能力 | 开源版单节点，无内置分布式/副本/水平扩展 | 依赖 PostgreSQL 生态扩展，分片复杂度会上升 | 原生分布式，支持副本、水平扩展、多租户 |
| 事务与业务数据 | 弱 | 强，向量与业务数据同库，ACID/元数据过滤直接 SQL | 独立系统，业务数据一致性需应用层协调 |
| 企业支持 | 无企业级支持包 | 依托 PostgreSQL 成熟生态 | 有企业版和商业支持，但成本与复杂度更高 |
| 适合项目 | POC、Demo、小规模内部工具、快速验证 RAG | 已有 PostgreSQL、百万级以内知识库、业务数据与向量需同库 | 千万级以上、多租户、高可用、复杂标量过滤、大规模企业知识库 |
| 主要风险 | 单节点瓶颈、持久化/内存问题、缺企业支持 | 超 500 万后扩展复杂，索引构建慢，无 GPU 加速 | 小规模使用运维成本过高，系统复杂度数量级上升 |

### 2. 推荐决策顺序

| 优先级 | 决策规则 | 结论 |
|---|---|---|
| 第一优先 | 已有 PostgreSQL，且向量规模百万级以内 | 选 pgvector |
| 第二优先 | 无 PostgreSQL，或不想在业务库增加向量负载，百万级以内 | Chroma 可过渡，但不建议终态；更稳妥评估 Qdrant |
| 第三优先 | 满足以下至少两项：千万级以上、多副本高可用、独立扩缩容、多租户复杂过滤、有专门运维人力 | 才值得引入 Milvus |
