# Vibe Coding 自然语言编程

## Vibe Coding 自然语言编程-模式
- 字面意思：氛围编程，我更喜欢叫凭感觉编程、用自然语言编程。
- 开发流程：用自然语言描述需求，引导AI快速生成代码、运行和修改代码，强调快速试错与结果导向。

## SDD 规范驱动编程-模式
- 规范驱动开发（Spec-Driven Development）
- 开发流程：先明确需求、架构方案、接口、原型设计等规范，再引导AI按照规范进行开发，最后逐项验收确保结果符合预期。

## 两种AI编程模式选型
- **个人项目**：`Vibe Coding 为主`，目的是快速低成本开始，满足个人需求即可。
- **企业项目**：`SDD + Vibe Coding 配合工作`，Vibe Coding快，SDD稳。
    - 推荐流程：Vibe Coding设计原型/快速验证想法 -> SDD项目设计与规范/确定方案 -> Vibe Coding 快速开发、运行和修改代码 -> SDD 测试验收/部署 -> 持续版本迭代。 

## 比喻说明
> 首先一句话：AI是助手，人是决策者。
- 你是老板，AI-agent 智能体工具是员工，一个超强大脑+能用电脑干活的员工。
- 你会不会编程都行，你作为老板需要表达出项目需求，你的要求，你的约束，让AI根据你的要求生成产品文档来约束整个项目，遇到不确定时，给你说明技术方案优缺点，给你专业建议，由你来拍板。所有产品文档问题点确定后，让AI按照步骤开发，有问题让你来决策，直到完成任务。

## 开发过程
总体流程：AI需求确认->产品文档->AI生成交互原型设计->AI架构方案设计->AI开发->AI测试&验收->部署

- 先开plan模式：先定产品文档，开发方案，让AI帮你生成产品文档，跟AI沟通确定方案
  - 他会生成开发步骤 1，2，3，4... （正式开发会按这个步骤）
- 根据确定的产品文档，AI生成交互原型设计（html,css,js），有问题就改问题
- 根据方案+原型设计，再继续生成架构方案设计：包含架构设计图，数据库设计，接口设计等
- 开始开发
- 等待：AI开发中，遇到方案选型问题会问你，你拍板选择即可
- 等待结束：人工去体验和检查功能，有bug就交给AI解决
- 完成后：继续做接下来的工程化
  - 增加git仓库管理
  - 增加单元测试
  - 部署
  
## 工程化
在整个开发过程中的各个环境可以沉淀出skill、sub-agent, 让我们复用并提效，甚至跨项目复用
1. skill: 技能，一些工作能力，例如产品经理会梳理需求生成产品文档，原型，设计师会画UI图，架构师会设计项目架构，程序员会开发代码，测试会写测试用例验证问题，运维会部署项目等等，`他们都能沉淀下来skill，帮助项目高效实现特定任务`，当然，`还是需要专业的人来审查结果是否正确且可行。`
2. sub-agent: 一个子agent相当于一个数字员工，主agent相当于老板，负责自动调度，就是派活。
    - 特点：子agent是隔离的独立上下文，任务完成把结果给主agent, 不污染主对话上下文。
    - 一个数字员工会调用skill或各种工具完成一类任务，如产品经理会调用产品文档skill+绘制原型skill, 架构师会调用架构设计skill.
    - 用户在主agent提任务如帮我生成产品文档，主agent模型自动派活给产品经理agent
    - 优点：子agent上下文隔离，保证主agent上下文干净；可并行，用通信token成本换效率成本。
    - 缺点：子agent开的越多，通信成本越大；简单任务反而更慢；多agent开会的话，agent越多越难达成一致。
    - 适用场景：
        - **执行型任务**，可以用，别滥用，可以预定义几个子agent, 描述好适用场景，主agent会根据场景自动派活，这样上下文干净，还省事。
        - **决策型任务**，可以用，但需控制人数。需求评审、方案取舍、复杂问题排查等`需要多双眼睛互相质疑`的情况，适合关键是视角不同，不是人多，一般2-3个角色就够了，一般从架构、风险、事实等视角观察。防止一个agent找到答案就算完成任务的情况。
- 一些skill技能：
    - 设计UI：`/ui-design`, 根据已确认好的产品文档，利用html,css,js生成可交互的UI设计，不确定的可以问我，给出方案优缺点和建议，让我来决策。
    - 启动应用：`/run-app`，启动前端app, 甚至启动前后端+数据库等，一行命令启动所有服务。
    - 单元测试：`/unit-test`, 检查项目单元测试是否编写，没编写就补充，编了就执行，并返回单元测试报告，放到results文件夹
    - 书写注释：`/comment-check`, 检查项目注释是否书写规范,
        - 后端（如 Java/Go）：通常更强调对 公共 API、复杂算法、数据结构 进行文档注释（如 Javadoc），方便生成接口文档。同时，方法内部的复杂逻辑块也需要必要的行内注释。
        - 前端（如 JS/TS）：除了函数和组件的说明，注释常用来解释 UI 状态变化的原因、特定浏览器兼容处理 或 复杂的状态管理逻辑。对于显而易见的 DOM 操作或简单赋值，通常不需要注释。
    - 质量审查：`/quality-review`, 检查项目代码与核心功能是否正确，业务验收是否过关。bug类型和梳理统计，把结果放到results文件夹。
    - git提交： `/git-saved`， 负责将本地开发好的代码，`git add .`、`git commit -m '提交信息'`
- 一些sub-agent：根据用户问题，主agent会自主调用合适的子agent员工去干活。
    - git提交守门员：具备`/quality-review`和`/unit-test`，通过后调用`/git-saved` 提交代码的能力
    - 质量审查员：具备`/quality-review`和`/comment-check`能力
